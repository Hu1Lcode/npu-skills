# P5 · 优化迭代：先无侵入 · 单变量 · 固化

这是优化的核心循环。每轮：**读证据 → 只改一个变量 → 复测性能和精度 → 判三态 → 固化进基线 → 回到 P4**。

## 为什么一次只改一个变量

多个改动一起上，无法归因是哪个起了作用、哪个其实有害；也无法在某项导致精度回归时定位。单变量 + 每次复测，才能把"有效"沉淀为可复用的确定收益。

例外：P3 的**环境变量组**作为一个优化点成组测量（用户已确认）；融合算子必须逐个替换、逐个测量。

## 两阶段优化与侵入性分级（用户已确认）

**第一阶段 · 无侵入（自动实施）**：只做两类——

1. **环境变量组**：按场景选组、成组测量；
2. **融合算子 / 算子后端替换**：先扫描本机 `torch_npu` 实际导出接口（`scripts/scan_fusion_ops.py --detail`，`--detail` 可看函数签名与首行说明），只替换 P4 热点上的原语；保留原实现和开关，优先用独立补丁/包装层/monkey patch 落地，尽量不改模型主体结构。

**第二阶段 · 有侵入（只列清单，交用户决策）**：除上述两类外的所有改动。

| 类别 | 典型手段 | 处理 |
|---|---|---|
| **无侵入（自动）** | 环境变量组；`torch_npu` / mindiesd 等框架融合算子替换、attention backend 等算子后端切换（接口不变、有原实现回退） | 自动实施、逐点测量、固化 |
| **有侵入（只列清单）** | 局部代码改写（VAE 快路径、输入预转换、缓存复用）、模块/接口替换、并行范式调整（TP/SP/CFG/CP）、图模式、量化、Attention Cache、稀疏注意力、多流/权重预取、VAE patch parallel、大规模重构 | 不自动实施；按预期收益降序输出决策清单，用户批准后按单变量流程实施 |

> 用户明确要求：只自动做**环境变量与融合算子**两类无侵入项；其余改动无论收益大小都先列清单，由用户拍板。

**侵入性清单排序规则（从高到低，收益统一折算为 E2E 时延或 s/step 的百分比）**：
1. 优先用 P4 直接证据估算：`热点算子/阶段耗时占比 × 预计可消除比例`（如 attention 占 `dit_denoise` 60%、换后端预计省 20% → E2E 约 8–10%）；
2. 其次用经验库/同类模型实测收益（注明来源与适用条件）；
3. 最后是理论估算（Roofline、FLOPs、通信量），必须标"待验证"。

收益接近时，侵入程度低、工作量小、依赖少的排前面。清单每项必须写：优先级、优化点、证据、预期收益及依据、侵入程度、改动位置 `file:line`、工作量、风险、依赖、回退方式。

## 实验协议

1. 从**当前固化基线**出发（不是从开箱出发，否则会丢已得收益）。
2. 只应用一个改动（一个环境变量组 / 一个融合算子替换）。
3. 用 P2/P7 同口径复测（筛选可用短步：推理 5-step、训练 10-step；定稿必须完整 pipeline / 原始启动脚本；同 warmup/步数/batch/机器状态）；建议重复 ≥ 3 次取中位数，抵消抖动。每次复测必须同时记录 **E2E 与全部阶段耗时**。
4. **增益判定**：相对当前基线提升要显著大于运行间抖动（经验：> 3%–5% 且重复可复现才算数）；同时通过精度校验。
5. 三态处理：
   - ✅ 有效且精度通过（`cosine ≥ 0.999`）→ **固化**；更新"当前基线"为该结果；git 仓库 `git commit`（`opt(N): <名称>`），非 git 仓库更新 `artifacts/backups/` 与 `changes.log`。
   - ❌ 无效 / 负收益 / 精度回归 / 在噪声范围内 → 否决，回滚。
   - ⚠️ 冲突 / 需要多方案取舍 → 不自行决定，记"待决策"交用户（侵入性方案一律走 P5b 清单，不进入本实验循环）。

## 固化产物

- git 仓库：每个已固化优化点一个 commit，消息格式：`opt(01): attention 改用 npu_fused_infer_attention_score`；非 git 仓库见下节"每点备份与回滚"。
- `artifacts/applied.patch` 可作运行态备份，但正式交付以 P8 的 `patches/NNN-*.patch` + `all.patch` 为准。
- `artifacts/env.applied.sh`：所有已固化环境变量（可 `source`）。
- `optimization_ledger.md`：每次实验一行，含 before→after 的 **E2E 时间与各阶段耗时（中位数/P50/P95/占比）**、`standalone_gain`（分卡并行筛选的单点增益）、`stacked_gain`（串行集成后的增量）、`experience_id`（若候选来自经验库）、`experience_result`（该经验在本次是否有效）、原因/证据、精度结论（统一 cosine ≥ 0.999）、状态。最终报告以 `stacked_gain` 为准。
- `invasive_candidates.md`：所有未实施的侵入性候选，按预期收益降序；每项含优先级、证据、预期收益及依据、侵入程度、改动位置、工作量、风险、依赖、回退方式（模板见 `assets/invasive-candidates-template.md`）。表头：

  | 优先级 | 优化点 | P4 证据 | 预期收益（依据） | 侵入程度 | 改动位置 | 工作量 | 风险/副作用 | 依赖 | 回退方式 |
  |---|---|---|---|---|---|---|---|---|---|

## 非 git 仓库：每点备份与回滚（用户已确认）

非 git 仓库没有分支/commit 兜底，必须让**每一个优化点都能单独回退**：

1. **P0 完整备份**：`rsync -a --exclude 'perf_reports' <repo>/ perf_reports/<date>/backup_src/`（无 rsync 时用 `tar --exclude='./perf_reports' -cf - . | tar -xf - -C <backup_dir>`），作为最终兜底；记录备份时间与源路径。必须排除 `perf_reports/` 自身，避免递归拷贝。
2. **每点文件级备份**：动手前把本点将修改的文件按原相对路径复制到 `artifacts/backups/<opt_id>/`；在 `artifacts/backups/backup_manifest.json` 记录 `opt_id`、原路径、备份路径、`sha256`、时间、改动范围。
3. **每点 diff 即 patch**：用 `a/<相对路径>`、`b/<相对路径>` 标签生成可 `patch -p1` 的 diff——`diff -uN --label a/<rel> --label b/<rel> artifacts/backups/<opt_id>/<rel> <repo>/<rel> > patches/NNN-<name>.patch`（`-N` 兼容新增文件）；新增文件在 `backup_manifest.json` 记 `change_type: add`；追加 `artifacts/changes.log`（时间、优化点、文件、原因、回退命令）。
4. **回退**：`patch -R -p1 < patches/NNN-*.patch`，或 `cp -a artifacts/backups/<opt_id>/. <repo>/`；回退后核对 `sha256` 与备份一致。
5. 即使某个优化点被否决，也保留其备份、diff 与台账记录，不要删除证据。

## 候选看板（多候选并行筛选时）

单候选循环直接用上面的三态即可。当 B 一次给出多个候选、或开启分卡并行筛选时，为每个候选建一行看板，状态用：

| 状态 | 含义 | 与本技能三态的对应 |
|---|---|---|
| `待决策` | 有侵入（环境变量/融合算子以外）或存在冲突，等用户拍板 | ⚠️ 待决策 |
| `待实现` | 用户已批准（或属无侵入项），尚未实施验证 | —（进入实验） |
| `通过` | 已实施、性能收益明确、精度与回退均验证通过 | ✅ 有效并固化 |
| `淘汰` | 无效/负收益/精度回归/实现失败/被更优方案替代 | ❌ 否决 |

看板每行至少记录：`plan_id`、来源（profiling 证据 / 经验库）、方案描述、预期收益、风险、侵入性、互斥组、可叠加性、状态、证据链接。

- **互斥组**：同一段代码或同一机制的两种改法互斥（例如"融合算子改写 attention"与"多流切分 attention"、"图模式"与"多流"）。同组最终只能留一个 `通过`。
- **可叠加**：必须逐个应用并记录 `stacked_gain`，最终验收前实测组合效果；组合退化时追加组合验证轮，必要时淘汰较差一方。
- **派生**：实施/复核中发现新路径，追加新的 `plan_id`，不覆盖旧候选。

## 何时需要重采 profiling

不是每轮都要重采。判断标准：**现有 profile 还能不能支撑接下来的收益判断**。

需要重采：
- 上一轮改动改变了算子下发时序、计算图结构、dtype 或 layout（多流、融合、图模式、量化基本都属于这类）；
- 现有 profile 与当前代码已对不上，或 reviewer 认为证据不足；
- 切换到新方向/新热点模块；
- 终裁某方案或进入最终验收前（最终代码路径必须有一份同口径的最新 profile 与 baseline 对照）。

可以不重采：
- 只动了开关或参数，未改变算子与计算结构，且仍用同一份数据对照；
- 改动与性能结构无关（纯精度修复、日志等）。

## 最终验收清单（P8 前）

- [ ] 看板无 `待实现`/`待决策` 遗留（待决策项必须明确"本次不实施"并写进报告）；
- [ ] 所有 `通过` 项已在最终代码路径真实生效；
- [ ] 所有 `淘汰` 项已回退或开关已关闭；
- [ ] 互斥组状态自洽；
- [ ] 可叠加组合已实测；
- [ ] 精度/功能满足初始口径；
- [ ] 最终性能与 baseline 同场景、同口径对比（打点关闭）；
- [ ] 确认无法再派生出仍有潜在收益的新候选。

## 冲突与待决策（一定交人工）

典型：
- `PYTORCH_ALLOC_CONF` 与 `PYTORCH_NPU_ALLOC_CONF` 互斥（同义，不能同设）。
- 融合算子与 dtype/精度要求冲突（如 `npu_rms_norm` 只接受 fp16/bf16 输入，与 fp32 精度要求冲突）。
- 两个优化互相抵消（一个改善通信、一个破坏重叠）。
- 需要改模型代码的侵入性方案（P5b 清单中的项）。

处理：在台账标 `⚠️ 待决策`，汇总成决策清单给用户（列：冲突点、各方案收益/代价、建议），等用户选择后再动。

## 循环终止

达标（目标指标满足）或持续无更多无侵入收益时停止；剩下的侵入性/待决策项按预期收益降序进入最终报告，不自动实施。

## 一轮的伪代码

```text
while not reached_target:
    prof = collect_and_analyze(current_state, steps=3)   # P4
    cand = pick_non_invasive_candidate(prof)             # 只从 env / 融合算子中选
    if not cand:
        write_invasive_decision_list(prof)               # 按预期收益降序，交用户
        break
    apply_one(cand)
    before, after = remeasure()                          # 同口径, >=3 次中位数
    if significant(after) and precision_ok():
        freeze(cand); commit_opt(cand); update_baseline(after)
    else:
        rollback(cand)
    if conflicting(cand):
        record_decision_item(cand)                       # 交人工
```
